# Данные для tiny-turbo

Эта рекомендация отвечает на узкий вопрос: что дать `tiny-turbo` (62,6M
параметров), если на RX 9070 XT есть одни сутки и измеренные 18k токенов/с.
Это не универсальный рейтинг корпусов и не рецепт для `base`.

## Бюджет суток

Production-рецепт `tiny-turbo` читает
`4 × 32 × 1024 = 131 072` токена на optimizer step.

| план | steps | токены | чистое обучение при 18k tok/s |
| --- | ---: | ---: | ---: |
| Chinchilla, ≥20 токенов/параметр | 9 556 | 1 252 524 032 | 19,33 ч |
| рекомендуемый суточный прогон | **11 200** | **1 468 006 400** | **22,65 ч** |
| физический потолок суток | 11 865 | 1 555 169 280 | 24,00 ч |

`11 200` оставляет около 1 ч 20 мин на autotune первых GPU-ядер, validation,
checkpoint и неизбежный разброс throughput. Если эти расходы вынесены за рамки
суток, можно взять `11 865`. Дефолтные `12 500` шагов — 1,6384B токенов и
25,28 ч при 18k tok/s, то есть они не оставляют времени на startup и validation.

Подготовленный корпус должен содержать хотя бы столько train-токенов, сколько
просит прогон. Это не epoch: loader выбирает равномерные случайные смещения, и
на слишком маленьком корпусе начнут повторяться окна.

## Что известно к июлю 2026

Лучший открытый ориентир именно для класса маленьких моделей — данные
[SmolLM2](https://arxiv.org/abs/2502.02737). Его 135M-вариант обучался на 2T
токенов: 1 065,6B DCLM-Edu, 710,4B FineWeb-Edu, 125B Stack-Edu, 40B
InfiMM-WebMath, 34B FineMath и 30B Cosmopedia v2. Готовая
[10B-выборка этой смеси](https://huggingface.co/datasets/EleutherAI/SmolLM2-135M-10B)
публикует те же источники и их объёмы.

Это согласуется с тремя независимыми наблюдениями:

- [DCLM-Edu](https://huggingface.co/datasets/HuggingFaceTB/dclm-edu) создан
  специально для 135M/360M SmolLM2; на 360M его фильтр улучшил knowledge и
  reasoning относительно DCLM и FineWeb-Edu.
- [FineWeb-Edu](https://arxiv.org/abs/2406.17557) существенно улучшает MMLU и
  ARC относительно общего web-корпуса при одинаковом числе токенов.
- Однокарточный эксперимент
  [L20-Edu-135M](https://arxiv.org/abs/2606.22189) в 2026 году снова получил
  лучший data-efficient результат через 10B FineWeb-Edu, затем 3B смеси
  education/math/code/reasoning. Авторы отдельно не называют это контролируемым
  scaling law, поэтому переносить их 77/23 буквально на 1,47B нельзя.

### Рекомендуемая смесь

Для общей англоязычной модели, а не code-модели:

| источник | доля train-токенов | зачем |
| --- | ---: | --- |
| DCLM-Edu (`edu_int_score ≥ 3` в идеале) | **55%** | широкий качественный web, лучший small-model ориентир |
| FineWeb-Edu | **35%** | образовательный web и фактическое покрытие |
| FineMath-4+ | **5%** | математика и структурированное рассуждение |
| Cosmopedia v2 | **5%** | простой синтетический учебный текст |

Это округлённая SmolLM2-подобная смесь без кода, с осторожно увеличенной долей
специализированного текста для короткого прогона. Для модели, которая должна
писать код, заменить 5% Cosmopedia на 5% подготовленного Stack-Edu/Python.
Опубликованный Stack-Edu содержит SWHID, а не сами исходники: их сначала нужно
получить из Software Heritage по инструкции dataset card. Нельзя передавать его
metadata parquet в `prepare` как будто там уже есть поле `text`.

### Почему не исходный пример

- **30% TinyStories — слишком много.** Корпус создан, чтобы модели меньше 10M
  параметров научились связным детским рассказам
  ([исходная работа](https://arxiv.org/abs/2305.07759)). Он хорош как отдельный
  smoke-test или узкая story-модель, но 30% суточного бюджета учат жанру и
  ограниченному словарю вместо общего знания.
- **Отдельные 5% Wikipedia не обязательны.** DCLM-Edu и FineWeb-Edu уже дают
  широкий фактический web. Без cross-source near-dedup отдельная Wikipedia
  также может повторить документы, присутствующие в web-корпусах. Если
  энциклопедический стиль является целью, заменить ею 5% FineWeb-Edu и измерить
  per-source holdout, а не просто добавить сверху.
- **Cosmopedia полезна как примесь, не как основа.** Это синтетический текст
  Mixtral-8x7B; его структура удобна маленькой модели, но большая доля переносит
  стиль и ошибки teacher-модели.

## Воспроизводимый суточный рецепт

По одному parquet каждого источника уже достаточно для долей суточного
корпуса; это примерно 6,5 GB загрузки вместо десятков гигабайт:

```sh
hf download HuggingFaceTB/dclm-edu --repo-type dataset \
    --include "data/000_00000.parquet" --local-dir data/dclm-edu
hf download HuggingFaceFW/fineweb-edu --repo-type dataset \
    --include "sample/10BT/000_00000.parquet" --local-dir data/fineweb-edu
hf download HuggingFaceTB/finemath --repo-type dataset \
    --include "finemath-4plus/train-00000-of-00064.parquet" \
    --local-dir data/finemath
hf download HuggingFaceTB/smollm-corpus --repo-type dataset \
    --include "cosmopedia-v2/train-00000-of-00104.parquet" \
    --local-dir data/cosmopedia
```

Подготовка измеряет доли **после токенизации**. Вес относительный и не обязан
суммироваться в 100; `55:35:5:5` и `11:7:1:1` эквивалентны:

```sh
cargo run --release -- tokenizer \
    data/dclm-edu data/fineweb-edu data/finemath data/cosmopedia \
    --vocab-size 8192

cargo run --release -- prepare \
    --mix 55:data/dclm-edu \
    --mix 35:data/fineweb-edu \
    --mix 5:data/finemath \
    --mix 5:data/cosmopedia \
    --tokens 1468006400 \
    --out data/tiny-turbo-day

cargo run --release --no-default-features --features vulkan -- \
    train tiny-turbo --data data/tiny-turbo-day --out runs/turbo-day \
    --steps 11200
```

`prepare` сохраняет целые документы, поэтому последний документ немного
переводит корпус через `--tokens`. Планировщик всегда выбирает источник,
который сильнее всего отстаёт от своей доли по уже записанным train-токенам.
Каждый источник имеет собственный детерминированный holdout 1/200 документов:
глобальный счётчик мог бы синхронизироваться с периодом весов и складывать весь
validation в один источник.

Рядом с `train/` и `valid/` пишется `mix.json`: запрошенные и фактические доли,
токены, документы и исходные байты каждого пути. Это receipt эксперимента;
сохранить его рядом с checkpoint и зафиксировать revision/SHA-256 загруженных
parquet так же, как делает `examples/fineweb_soak.sh`.

## Что считать результатом

Для первого прогона важнее не один итоговый loss:

1. validation bits-per-byte должен устойчиво падать;
2. сравнить отдельные holdout каждого домена, если меняются веса;
3. проверить короткие генерации на factual prose, math и связность;
4. менять только одну долю за A/B и сохранять тот же tokenizer, seed и число
   train-токенов.

У 62,6M недостаточно ёмкости, чтобы получить все способности больших SmolLM2
за 1,47B токенов. Цель суток — честно сравнить архитектуру и данные, а не
выдать высокий score на узком TinyStories за универсальную модель.
